# 同一批请求，全程采集 Decoder

这版替换原来的 5 秒采样版。保留模式选择、进度显示和多轮结果平均值计算。

## 直接运行

将压缩包内所有文件放到服务器 `/workspace/ycp/vllm_serve_run/`，覆盖同名的采集工具。
原有 Proxy、Prefiller 和 Decoder 启动脚本继续放在这个目录。工具无需放到 vllm-ascend 源码目录。

```bash
cd /workspace/ycp/vllm_serve_run/
bash ./automatic_benchmark_profile.sh \
  --modes bl,lb,dynam \
  --rounds 1 \
  --num-prompts 100 \
  --dataset-path /实际路径/数据集.jsonl
```

三种模式各执行同一份数据集的前 100 条请求，并各采集完整执行过程。100 是示例，可以修改。
不会复制请求补足数量；数据不足时在启动服务前报错。
全程采集默认 1 轮；如需 10 轮及其平均值，使用 `--rounds 10`。
同一模式的全部轮次记录到一份采集中，包含客户端准备和轮间等待。轮间等待可用 `--round-interval 0` 关闭。

Decoder 地址可用 `PROFILE_DECODER_URL=http://实际IP:13701` 设置。
Tokenizer 路径可用 `TOKENIZER_PATH=/实际模型目录` 设置。客户端随机种子默认为 0，可用 `--seed 123` 修改。

## 请求如何保持一致

1. 启动服务前，把数据集前 N 条保存为 `workload/requests.jsonl`，各模式和轮次始终读这一份副本。
2. 保留原始 prompt 和每条请求各自的 `output_tokens`，不会把所有请求改成同一长度。
3. 固定顺序，禁止打乱和自动重复补足。固定客户端种子、并发上限和请求速率。
4. 强制 `ignore_eos=true`，避免提前遇到 EOS 而少生成 token。采样温度为 0。
5. 使用 `--num-warmups 0 --ready-check-timeout-sec 0`，不发送额外的生成测试或预热请求。服务就绪仍由启动日志检查。
6. 每轮检查成功数、失败数、逐请求实际输出长度和输出总量，与首个有效运行逐条核对输入 token 长度。
7. 少完成请求、输出提前截断、输入长度不一致，均报错停止，不会标记为工作量一致。

数据集沿用 custom JSONL 格式，每行例如：

```json
{"prompt":"第一条请求的原文","output_tokens":128}
{"prompt":"第二条较长请求的原文……","output_tokens":512}
```

`output_tokens` 必须是正整数。请求 SHA256、源行号和各条输出目标保存在 `workload/workload.json`。
实际输出长度来自 vLLM benchmark 详细结果；失败时查看对应的 `*.validation.json`。
相同请求不表示各卡分到相同数量的请求，也不表示 batch 相同。实际到达时刻还受网络、并发上限和处理速度影响。

## 全程采集如何启停

每种模式的 Decoder 就绪后，先向 Decoder `/start_profile` 发请求，成功后才启动 benchmark。
全部轮次完成后调用 `/stop_profile`，等数据写出后再释放 Decoder。
不依赖进度百分比，不设固定秒数。旧的 `PROFILE_SECONDS` 和 `PROFILE_PROGRESS_PERCENT` 会被明确忽略。

停止接口默认不设超时，因为全程数据的写出可能超过旧版 600 秒。
如需自设上限，可用 `PROFILE_STOP_TIMEOUT=1800`，单位为秒。
压测或工作量校验失败时也尝试停止并写出 profiler。停止失败后不重复调用，失败采集不能当作完整结果。
只给 Decoder 加 profiler 并向它的端口启停，Prefiller 不启用采集。当前 Decoder DP=8、TP=1 的部署中，dp0～dp7 全部属于 Decoder。

## 结果在哪里

```text
profiling/run_时间_主脚本PID/
├── run_config.json                     请求数、轮数、seed、并发、速率和预期工作量
├── workload/
│   ├── requests.jsonl                  所有模式共同使用的请求副本
│   ├── workload.json                   请求指纹及各条输出目标
│   └── reference_input_lens.json        首个有效运行的逐请求输入长度
├── launch_scripts/                     本次使用的 Decoder 启动脚本副本
├── benchmark_results/
│   ├── ..._bl_round1.json               原始详细结果；其他模式同样保存
│   └── validation/
│       ├── workload_comparison.csv      各模式/轮次的核对和吞吐
│       └── bl_round1.validation.json    单轮核对；其他模式同样保存
├── bl/
│   ├── capture_events.jsonl             profiler 启停请求和返回时间
│   └── dp0_..._ascend_pt/ ... dp7_..._ascend_pt/
├── lb/ ...
└── dynam/ ...
```

benchmark 输出和多轮平均值仍保存在 `log/*_roundsN_模式.txt`。
HTTP 启停时间不是逐卡精确的 NPU 同步边界。

解析本次数据：

```bash
python3 ./分析采集数据.py ./profiling/run_这里替换为本次目录
```

如果继续使用之前的可视化工具，务必读取全部 Decoder DP：

```bash
python3 ./dyntra_profile_analyze.py \
  --input ./profiling/run_这里替换为本次目录 \
  --output ./完整对比报告 \
  --dp-ranks all
```

完整采集的数据量更大，首次可用能代表真实长短请求分布的一小批固定请求验证流程。
本地使用模拟服务检查流程；真实 NPU 的采集和导出仍需在你的服务器执行。

## 比较时保留的区别

本版固定请求和采集范围，保留现有 Decoder 脚本中的模式设置。
若要只归因于负载均衡算法，请统一模型、量化、max-num-seqs、max-model-len、max-num-batched-tokens、
图执行、prefix caching 和异步调度等公共设置。实际脚本副本保存在 `launch_scripts/`，便于核对。

worker profiler 仍不能自动量出独立调度进程内的全局状态 CPU All-gather，这项需单独计时。
Profiler 会影响性能。需要不带采集的对照时，使用同一命令并加 `PROFILE_ENABLE=0`，固定请求和逐条核对仍然执行。
